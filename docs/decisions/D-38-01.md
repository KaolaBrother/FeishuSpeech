# D-38-01: Review-first live preview and explicit original-target delivery

- Status: accepted and implemented; automated candidate validation complete; installed Release UAT pending
- Date: 2026-08-23
- Issue: #38
- Superseded in part by: D-39-01 for the editable review Return/Enter keyboard policy only, and
  D-40-01 for the strict-AX-only review startup/delivery admission; this record's exact-cursor
  route, clipboard lifecycle, capture/journal, recognition/retry/replay, and independent
  review-axis decisions remain in force
- Conditionally supersedes: D-25-01's rejection of a transcript preview/edit/send surface and
  D-27-01's immediate target-writing assumption, only while `reviewBeforeInsert == true`
- Retains: D-27-01 opaque-snapshot and action-2 authority; D-28-01 independent capture/journal and
  recognition/consumer lines; all retry, replay, release-drain, privacy, and generation fences
- Compatibility: when `reviewBeforeInsert == false`, D-27-01 remains the output contract and
  `autoInsert` keeps its historical meaning

## Context

The issue #27 route writes recognized snapshots into the destination application while Fn remains
held. That route is still useful as an explicit compatibility mode, but it does not let the user
see the complete recognition result, edit it, and make a final value decision before any text is
inserted.

Issue #38 adds a KaolaTerminal-aligned review lifecycle without copying KaolaTerminal's terminal
destination, iOS gesture controller, or transport implementation. The macOS app needs one visible
surface from live streaming through sealing and editing, and the user's explicit confirmation must
be the only authority to write the edited draft through the destination authority captured at
interaction start. D-40-01 adds an application-bound current-focus authority when an ordinary
non-secure target cannot provide the strict AX cursor.

The existing stability boundary is not negotiable. `MainViewModel` already has two causally
separate asynchronous data lines:

1. capture drains recorder PCM into `HoldPacketJournal`; and
2. recognition creates and retries sessions, replays the journal, consumes live packets, and
   settles action 2.

The review UI is a third axis. It may observe already-owned recognition values, but neither data
line may wait for preview rendering, window activation, editor focus, dismissal, or delivery.

## Decision

### Output-mode sampling and migration

`AppSettings.reviewBeforeInsert` defaults to `true`. Both the public settings model and the private
stored payload decode it with `decodeIfPresent(... ) ?? true`, so an older valid JSON payload that
lacks the field migrates to review-first without making the remaining preferences or Keychain
credentials fail decoding. An explicit `false` value round-trips and selects compatibility mode.

The coordinator samples `reviewBeforeInsert` and `autoInsert` once when an accepted Fn interaction
starts:

- `reviewBeforeInsert == true` selects `.reviewFirst`; explicit review confirmation is required
  regardless of `autoInsert`;
- `reviewBeforeInsert == false` selects `.compatibility(autoInsert:)` and preserves D-27-01; and
- a Settings change during a hold or while a draft exists affects only the next interaction.

An unresolved review authority rejects a new Fn interaction. The new hot-key identity returns to
idle without starting replacement audio/network work and cannot displace the existing draft.

### Three independent state axes

```text
capture axis:      idle -> streaming ---------------------> sealing -----------> idle
                              | PCM -> ingress -> journal

recognition axis:  idle -> factory/send/retry/replay -----> drain/action-2 ----> idle

review axis:       idle -> streaming(read-only) ----------> sealing(read-only)
                                                                          |
                                                                          v
                                                                     editable
                                                                     |      |
                                                               confirming  discard
                                                                     |      |
                                                                     +-> idle
```

The capture-drain and recognition-consumer tasks remain distinct roots. Review presentation adds no
buffer, stream, `AsyncSequence`, journal wake-up, retry admission condition, replay ordering rule,
or backpressure edge to either root.

Read-only streaming/sealing presentation is a cancellable, revision- and review-ID-gated
fire-and-forget `@MainActor` task. It yields once and may be replaced by a newer snapshot before it
reaches the presenter. A stale render, callback, generation, attempt, or review ID is a no-op.

Action 2 closes recognition admission and starts a separate review-transition task. Only that task
may wait for the existing recorder barrier and the bounded editable-window readiness check. The
terminal recognition receipt returns without awaiting either; capture/journal progress and the
recognition consumer never depend on UI readiness.

### Live preview, sealing, and same-panel editing

Review-first captures the destination before audio or network work. A safe exact AX cursor remains
the preferred binding. If strict AX capture misses for an ordinary non-secure target, D-40-01 binds
the complete original application and admits an application-bound current-focus confirmation route.
Global or affirmatively secure input, lost Accessibility trust, incomplete identity, PID reuse, and
identity drift still fail closed; the route never arms a compatibility writer or an ambient-
current-focus fallback.

Once capture succeeds, `TranscriptionReviewState` progresses as follows:

```text
idle
  -> streaming(preview: "")
  -> streaming(preview: latest complete changed snapshot)
  -> sealing(preview: latest snapshot)             physical Fn release
  -> editable(draft, isPossiblyIncomplete)          action 2 + recorder barrier
  -> confirming                                     explicit confirmation
  -> idle                                            delivery settlement
```

`ReviewWindowController` retains one `ReviewPanel` instance across these states. During streaming
and sealing it is nonactivating, cannot become key/main, ignores mouse events, and has no close or
editing authority. Empty streaming shows `正在聆听…`; sealing shows `正在完成识别…`.

Recognition responses remain complete opaque snapshots. Packet-index ownership prevents replay
from owning the same historical response twice; a contentless or equal value does not replace the
preview, while any newly owned changed value replaces it in full. No delta is appended.

Physical Fn release changes the existing panel to sealing without dismissing or recreating it. A
non-contentless action-2 value becomes the initial draft. If action 2 is contentless and a usable
opaque snapshot exists, that exact snapshot becomes the draft with `可能不完整`. If neither exists,
the review authority returns to idle without opening an empty editor.

Only after action 2 has frozen the draft and the recorder barrier has completed does the same panel
gain key/main-window authority, activate FeishuSpeech, and focus its multiline editor. Editable
readiness is bounded to two seconds. Failure to establish it copies the frozen draft once for
manual recovery, dismisses the surface, and does not affect the already-settled data lines.

### Human editing and exact-once confirmation

> Historical issue #38 note: this record originally specified bare Return as multiline editing. Issue
> #39 and [D-39-01](D-39-01.md) supersede only that editable-review keyboard policy in the current
> implementation; all other issue #38 decisions remain unchanged.

Unmodified Return (including keypad Enter) confirms the current multiline draft. Shift+Return and
Shift+Enter insert LF without confirming; Command+Return remains a compatibility confirmation.
Return during marked text is passed to the input method. The `输入` button confirms; `取消`, Escape,
and closing the editable window discard. Whitespace-only text remains editable and cannot confirm.

Discard revokes the review authority and performs no application activation, Accessibility write,
pasteboard mutation, or synthetic key event. Recognition callbacks arriving after the editable
transition cannot overwrite a human edit.

Confirmation synchronously validates and freezes the exact untrimmed draft, changes state to
`.confirming`, advances the review revision, and dismisses the panel before creating or awaiting the
delivery task. Repeated buttons, shortcuts, stale window callbacks, and late recognition therefore
cannot create a second delivery.

LF is accepted as multiline draft data without normalization. NUL, tab, carriage return, DEL, and
C1 controls are rejected before destination or pasteboard mutation.

### Captured destination authority

D-40-01 retains this complete application identity as the common review authority:

- positive PID, bundle identifier, executable URL, and finite launch date; and
- the accepted interaction generation plus captured safe security state.

The binding is either the preferred exact route — original PID, `AXUIElement`, and selected-text
range — or the explicit `applicationCurrentFocus` fallback, which contains no AX element or
selection. AX capture requires Accessibility trust, Secure Event Input off, an affirmatively
supported non-secure editable role/subrole, focused-element PID equal to the frontmost PID, a valid
selection, and settable focus and selection-range attributes. It does not query whether
`kAXSelectedTextAttribute` is settable and performs no AX setter.

Capture reads and validates the complete frontmost/running application identity before asking AX,
then revalidates both identities afterward. A strict exact result wins. An ordinary non-secure AX
capability miss admits only the already captured application identity. Global or affirmatively
secure input, lost trust, missing identity fields, PID reuse, identity drift, or any inconsistent
token fails closed before panel/audio/provider startup.

Confirmation never samples a substitute target. It requests activation of the captured application
once and waits at most two seconds. The exact binding sets focus only on the captured AX element,
verifies that exact element, restores and rereads the original selection, and then performs one
process-targeted Cmd+V transaction. The fallback performs no AX setter or later AX recapture. After
activation it requires two consecutive composite samples. Each sample reads Secure Input at the
start, the raw frontmost PID, the running and frontmost complete identities, and Secure Input again
at the end. Only then does it post one multiline-safe Cmd+V pair to the captured PID; postflight
uses the equivalent composite safety shape.

The fallback proves the original application, not the original control or caret inside it. After
reactivation it uses that application's current focus and cannot cross applications. PID reuse,
wrong-app activation, activation rejection/timeout, destination drift, unsupported/secure target,
AX failure, event-post failure, and postflight uncertainty all fail closed. The route never
retargets or automatically retries; `CGEvent.postToPid` has no application-level consumption
acknowledgement, so retry after uncertainty could duplicate text.

### Pasteboard lifecycle and manual recovery

Before successful review delivery overwrites the general pasteboard, it snapshots every
data-bearing type from every prior pasteboard item. Restoration is scheduled only after one
process-targeted Cmd+V pair and successful postflight validation. The bounded restoration
opportunity checks that the pasteboard `changeCount` still equals the value produced by this
transaction, and the concrete restore repeats that check immediately before clearing/writing.

An intervening third-party pasteboard change is therefore preserved. Event-post or postflight
uncertainty schedules no automatic restoration and no delivery retry. A current non-cancellation
delivery or editable-surface failure copies the exact frozen draft once for manual recovery and
uses fixed transcript-free feedback. Cancellation performs no recovery copy. Manual recovery
deliberately leaves the exact draft on the general pasteboard.

### Privacy and lifecycle cleanup

Transcript values exist only in in-memory review state, the visible text/editor, and the bounded
pasteboard delivery/recovery operation. They are not persisted in UserDefaults, Keychain, files,
state restoration, diagnostics, crash messages, notifications, window titles, accessibility labels
or help text, or transcript-derived hashes. The intended visible `Text`/`TextEditor` remains
naturally available to assistive technology; the transcript is not duplicated into metadata. Logs
use fixed lifecycle/outcome values only.

Reset, sleep/wake, permission loss, Secure Input, terminal failure, and cleanup revoke the review
ID and revision, cancel presentation/transition/delivery tasks, clear callbacks and transcript
state, and dismiss the panel. A stale task cannot remount the surface, deliver, or copy.

The existing `OverlayWindowController` and `RecordingOverlayView` remain status-only and unchanged.
The review surface is separate; issue #38 does not make the recording overlay transcript-bearing or
editable.

### Compatibility scope and precise supersession

When `reviewBeforeInsert == false`, no review panel or review destination is created. The existing
D-27-01 route continues to select its verified AX range owner or fixed-PID keyboard owner, reconcile
opaque snapshots while held and through release drain, and apply its sampled `autoInsert` value.
Its fixed-target, HID interference gate, LF/action-control split, no-copy-on-uncertainty, and
action-2 reconciliation remain unchanged.

Accordingly, this record supersedes only these historical assumptions while review-first is
enabled:

- D-25-01's conclusion that the destination application is always the editing surface and a
  preview/edit/send panel is unnecessary; and
- D-27-01's assumption that each changed snapshot is offered immediately to a target writer.

It does not erase those records or their compatibility route. D-27-01 remains authoritative when
review-first is disabled, and its opaque-snapshot/replay and release-drain rules remain shared by
both modes.

## Alternatives considered

- Make the existing recording overlay transcript-bearing and editable — rejected because its
  status-only lifecycle and owner UAT boundary are separate; the review state needs independent
  authority and stale-render fencing.
- Wait for panel rendering or editor focus inside capture drain or recognition consumption —
  rejected because UI/WindowServer progress would become audio or transport backpressure.
- Recapture whichever control is focused at confirmation time — rejected because review-induced
  application focus changes would redirect text.
- Write via `kAXSelectedTextAttribute` — rejected for the review route because explicit confirmation
  should produce one destination-owned paste transaction after restoring the original selection.
- Retry an uncertain paste — rejected because the first Cmd+V may already have been consumed.
- Always restore the prior clipboard after a delay — rejected because it could overwrite a user's
  or third party's newer clipboard contents.

## Consequences and verification boundary

- The default interaction now requires an explicit human value decision before target mutation;
  users can retain the previous continuous-output behavior by disabling `输入前预览`.
- Review-first needs a complete original application identity before recording. Exact AX capture is
  preferred, while an ordinary non-secure strict-AX miss may use D-40-01's application-bound
  current-focus fallback. Secure input, incomplete identity, PID reuse, and identity drift still
  fail closed; the fallback cannot prove the original control or caret.
- The same panel remains visible while held, during sealing, and into editing; its read-only phase
  does not take focus from the original application.
- Delivery is exact-once from the coordinator's authority perspective, but local event submission
  cannot prove that an arbitrary third-party application consumed Cmd+V.
- Successful review paste temporarily owns the general pasteboard during a bounded one-second
  consumption opportunity. Process termination in that interval may prevent restoration; manual
  recovery intentionally leaves the draft on the pasteboard.
- Focused issue #38 validation passed 59/59. The full suite executed 408 tests with 1 skipped and
  0 failures; Debug and Release builds, strict SwiftLint, diff checks, and static proof that the
  legacy overlay files were untouched also passed. Independent correctness and security/privacy
  reviews reported zero blocking findings.
- Those counts are retained as issue #38 historical evidence; the issue #39 keyboard correction and
  its 40/40 focused, 423 executed / 1 skipped / 0 failures evidence are recorded in D-39-01.
  D-40-01 separately records its 79/79 focused implementation suite and the remaining installed
  Release UAT boundary.
- Automated tests cannot prove real WindowServer activation/key-window behavior, microphone and
  credential-bearing Feishu recognition, Accessibility restoration across third-party apps, or
  actual `CGEventPostToPid` consumption. Installed Release owner UAT remains required.
