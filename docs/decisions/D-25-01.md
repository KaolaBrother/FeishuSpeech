# D-25-01: Cursor-bound streaming speech contract

- Status: Historical issue #25 contract; output identity and keyboard replacement are superseded by
  D-27-01, while D-26-01 remains historical context for retry and release sealing; installed
  Release UAT pending
- Date: 2026-08-03
- Issues: #25 (decision), #26 (implementation)
- Reference implementation: KaolaTerminal D-148/D-149, commits `96b9422` and `397ad67`
- Affected boundaries: hot-key state, audio ingress, Feishu transport, coordinator, text insertion, overlay status, lifecycle recovery

## Problem

Before this decision, FeishuSpeech recorded a complete utterance, called Feishu `file_recognize`
after Fn was released, then pasted one final string into whichever control was focused at that
later moment. The implemented interaction is different: after the existing 0.3-second Fn hold
gate, recognized text should appear at the original cursor while the user is still speaking. The macOS app does
not need KaolaTerminal's transcript preview, editable draft, or explicit send panel because the
destination application is itself the editing surface.

Streaming creates a new correctness problem. Feishu does not document whether an intermediate
`recognition_text` is a delta, an accumulated transcript, a stabilized segment, or a revisable
hypothesis. The app also cannot safely assume that the focused application, editable element,
selection, or cursor remains unchanged between responses. Blind append, backspace simulation,
or unqualified late insertion into the current focus can duplicate text, erase user edits, or
write speech into the wrong application. The first UAT pass also showed that making AX cursor
capture a prerequisite for recognition was too strict: applications without a confirmable AX
destination received no recording or streaming at all.

## Decision

> Supersession note: [D-27-01](D-27-01.md) is the current output contract. It restores opaque
> snapshot replacement, keeps packet replay ownership separate, and expressly supersedes this
> record's blanket rejection of synthetic Backspace: the generic keyboard route may delete only
> this hold's grapheme-counted owned tail as one guarded replacement transaction. D-26-01 still
> governs retry and release sealing where D-27-01 does not supersede it. The descriptions below
> remain historical context. Verified AX range ownership, generation safety, fixed PID/exact-element
> and Secure Input checks, fail-closed drift/uncertainty, privacy, and no whole-file fallback remain
> authoritative where they do not conflict with D-27-01.

### Post-UAT refinement

This section supersedes the original strict destination startup gate in this decision. Failure to
capture or confirm an AX cursor/focused element no longer rejects the interaction: audio capture
and Feishu streaming proceed without a destination token. Live AX range replacement remains
opportunistic where a safe target supports it. In the unbound case, the coordinator retains opaque
responses, samples Secure Input and the frontmost PID twice, and attempts to insert a non-empty
final exactly once into the current focus through a direct Unicode CGEvent. Successful delivery is
clipboard-free and has no cursor-position confirmation or claim that this was the startup focus.
An ordinary event-posting or PID-stability failure uses copy-only recovery.

This refinement does not weaken the independent safety boundaries. An affirmatively detected
secure text target or Secure Event Input remains fail-closed. A final containing C0/C1 control
characters remains copy-only rather than automatically pasted. `autoInsert=false` remains a
no-output mode. Installed Release UAT remains pending.

### Interaction state

The production interaction becomes:

`idle -> pending -> streaming -> sealing -> idle | error`

- `pending` preserves the existing 0.3-second accidental-press and modifier-combination gate.
- `streaming` owns one audio capture, one Feishu stream, and at most one cursor insertion session.
- Fn release or the 60-second cap enters `sealing`, stops capture, flushes the bounded audio tail,
  emits exactly one normal stream finish, and waits for the final response.
- `sealing` rejects a new Fn session. Cancellation, sleep/wake, reset, capture failure, or stream
  failure invalidates the whole generation before any asynchronous cleanup completes.

The overlay remains status-only. It may show listening, finalizing, unsupported-target fallback,
or failure feedback, but it never displays transcript text and never becomes an editing surface.

### Feishu stream

Production recognition uses `POST /open-apis/speech_to_text/v1/speech/stream_recognize` with
16 kHz mono signed Int16 PCM, Base64 JSON, `format=pcm`, and `engine_type=16k_auto`.

- Each hold owns one 16-character lowercase-letter/digit/underscore `stream_id`.
- Requests are strictly serial and use monotonically increasing `sequence_id` values beginning
  at zero.
- The first accepted non-empty packet uses `action=1`; later packets use `action=0`; normal
  release emits `action=2` exactly once; active cancellation attempts one bounded best-effort
  `action=3`.
- The target audio packet is 6,400 bytes, or about 200 ms. The established stream's final
  non-empty tail is at least 3,200 bytes, padding with PCM silence only when needed.
- A known invalid token may refresh and retry the same first packet once before any packet is
  accepted. After the stream is established there is no packet replay, parallel request,
  whole-file fallback, or whole-audio retry.
- Response identity echoes are not acknowledgements: code-zero responses may omit `data` or return
  any/malformed `stream_id` / `sequence_id` echo without failing the stream. The parser prefers
  `data.recognition_text`, falls back to `data.text`, and maps absent text to an empty event, matching
  KaolaTerminal's proven implementation. Nonzero business codes and malformed JSON remain failures.
- Every intermediate response is an opaque replacement value. The final `action=2` response is
  authoritative when it is non-empty.

### Bounded audio ingress

Audio callbacks are coalesced in capture order on the existing serial audio/buffer boundary
before entering a non-blocking async stream. At 32,000 PCM bytes per second, the 60-second cap is
1,920,000 bytes, or 300 full 6,400-byte elements. The ingress is bounded by bytes, never by raw
callback count. Sustained producer/consumer overload fails the current stream explicitly rather
than dropping or reordering audio.

### Cursor destination and provisional range

When `streaming` begins, the app probes and captures a
`CursorDestinationToken` from macOS Accessibility:

- the session generation;
- the original process identifier and focused `AXUIElement`;
- the original selected-text range;
- whether the element exposes settable selected-text and selected-range attributes;
- whether the element can return the string for a requested range.

Secure Event Input or an affirmatively detected secure text field is rejected before audio or
network work begins.
A live cursor session is available only when automatic insertion is enabled and the original
element supports safe range replacement and verification. With `autoInsert=false`, the capability
probe still protects startup, but the captured cursor session is discarded before any target or
pasteboard mutation. Live writes always address the captured element. If capture itself is
unavailable, the post-UAT unbound final-only path described below applies instead.

The first non-empty partial replaces the original selection and establishes one app-owned
provisional range. Each later partial replaces that complete range:

1. Verify the session generation, frontmost process, focused element, expected collapsed caret,
   and the exact previously written text in the owned range.
2. Select the owned range on the captured element.
3. Set its selected text to the new complete partial.
4. Read back the resulting caret and range text, then update ownership.

The owned range uses the range values returned by Accessibility after each write; it is not
calculated with Swift `String.count`. This avoids assuming that grapheme clusters, Unicode scalar
counts, and the target application's accessibility indexing are interchangeable.

Duplicate partials are no-ops. A shorter partial removes the superseded suffix because the full
range is replaced. AX notifications may invalidate a session early, but they are advisory;
pre-write and post-write verification remain authoritative because notification coverage differs
between applications.

Any focus, element, caret, selection, generation, or owned-text mismatch permanently invalidates
live output for that hold. Late events are discarded. The app does not use backspaces,
Shift+Arrow selection, or per-partial pasteboard writes as a fallback.

### Finalization and failure

- A non-empty final response replaces the same verified provisional range, moves the caret to its
  end, and releases ownership. No Return is synthesized.
- An empty final never deletes a non-empty visible partial. The last verified partial becomes
  ordinary editable text and the app reports that no final text was returned.
- A stream failure after a verified partial preserves that visible partial and releases ownership;
  deleting it after ownership is uncertain would risk deleting user content.
- A failure before the first successful write produces no target-application mutation.
- Any terminal provider or stream failure invalidates the generation, hides the overlay, and tears
  down once. The terminal event cannot fall through to normal finish, and an identical reflected
  hot-key error cannot re-enter teardown after the active identity is gone.
- Cancellation and lifecycle reset invalidate ownership first. They do not attempt destructive
  rollback after the target or range has become stale.

### Unsupported-target fallback

Final-only output has two modes. If the original non-secure editable element was captured but
cannot support verified range replacement, the stream retains only the latest opaque response in
memory. On normal finalization, a process-targeted pasteboard/Cmd+V path may insert the final string
once only if the captured PID, focused element, and security state are valid before and after
delivery. If that captured destination is stale or delivery is uncertain, the exact final value is
copied for manual recovery with fixed transcript-free feedback visible for two seconds.

If no AX cursor/focused element can be captured or confirmed, recording and streaming still
proceed. The coordinator retains opaque responses and, on a non-empty final, posts at most one
direct Unicode CGEvent to the current focus after two Secure Input samples and two matching
frontmost-PID samples. It does not touch the pasteboard on successful delivery, revalidate an
original destination, or confirm the current cursor position. It is deliberately final-only and
never redirects a partial. Ordinary PID instability or event-posting failure copies the final for
manual recovery; a security rejection performs neither input nor clipboard recovery.

In both modes, a final containing C0/C1 control characters receives no synthetic input and is
copied for manual recovery. A security rejection performs neither synthetic input nor clipboard
recovery.

Secure fields never use this fallback. The existing `autoInsert` preference remains authoritative:
when disabled, issue #25 does not grant a new cursor-writing capability. Changing or removing that
preference requires a separate product decision.

### Privacy and diagnostics

Logs and diagnostics may record typed failure categories, generation numbers, action/sequence
numbers, byte counts, and capability decisions. They must not record transcripts, partial/final
text, audio bytes, credentials or tokens, stream IDs, focused-control contents, application/window
titles, or clipboard payloads.

Provider authentication failure uses the fixed UI message `认证失败，请检查应用凭据`; its associated
backend detail does not cross the transport boundary.

## Alternatives considered

- Append every partial at the cursor — rejected because Feishu does not define partial responses
  as deltas and a revisable hypothesis would duplicate text.
- Delete the previous partial with synthetic Backspace or Shift+Arrow events — historical issue #25
  rejection. D-27-01 now permits Backspace only for the generic keyboard owner's own tail, counts
  Swift `Character` values after the exact common prefix, and suspends permanently on interference
  or uncertainty. Shift+Arrow and deletion outside that recorded ownership remain prohibited.
- Paste every partial — rejected because repeated clipboard ownership creates races, pollutes the
  undo history, and cannot prove that each paste reaches the original destination.
- Re-query the focused element for every partial response — rejected because a focus change would
  redirect revisable live text into a different application or field. The post-UAT unbound mode
  permits only one final delivery to the current frontmost focus when no AX destination existed.
- Retry or fall back to `file_recognize` after an established stream fails — rejected because the
  server may already have accepted an unknown prefix, making replay ownership ambiguous.
- Add the KaolaTerminal preview/draft/send panel — rejected because the macOS destination control
  is already the requested live editing surface.

## Consequences

- Supported editable macOS controls receive revisable text while Fn remains held, at the original
  cursor rather than at whichever control is focused on release.
- Live AX output is opportunistic and remains fail-closed when destination ownership cannot be
  proven; inability to establish that live capability no longer blocks recognition itself.
- Some applications will use final-only fallback because Accessibility support is not uniform.
- With no captured AX destination, the final-only fallback intentionally targets the current
  frontmost focus once and cannot confirm a cursor position.
- Target applications may create multiple undo records for repeated AX replacements; macOS offers
  no universal cross-application undo-grouping or marked-text contract. This is a documented UAT
  risk, not a reason to weaken destination checks.
- The whole-file API remains as compatibility-only code, but the production hot-key coordinator
  does not reference it and never uses it as a fallback for a streaming interaction.
- Issue #26 implemented the generation-owned coordinator, drain-aware byte-bounded ingress,
  strict serial transport, captured-element writer, captured and unbound final-only boundaries,
  fixed two-second completion feedback, and lifecycle cleanup. The post-UAT correction also makes
  terminal teardown exact-once, guarantees overlay dismissal, suppresses identical error
  republication, keeps authentication feedback private, and removes the response-side identity/data
  contract that caused the client to synchronously reject an `action=1` HTTP 200. The current
  complete macOS test run reports 190 passed, 0 failed, and 0 skipped.
- The 6,400-byte packet, 3,200-byte padded tail, lowercase stream ID, same-sequence first-token
  refresh, serial/exact-once terminal policy, and opaque replacement handling are conservative
  FeishuSpeech application rules, not vendor guarantees.
- Credential-bearing Feishu behavior and cross-application Accessibility compatibility remain live
  UAT gates. The latest installed-Release attempt obtained a token, sent `action=1`, and received
  HTTP 200 before the old client rejected its over-strict response contract. This proves endpoint
  reachability, not recognition success. Until the owner completes installed Release testing with
  the relaxed parser, this decision does not claim end-to-end streaming success, a broadly
  supported application matrix, or completed production UAT.
