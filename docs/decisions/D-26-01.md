# D-26-01: Resilient Fn hold and guarded continuous current-focus output

- Status: Implemented locally in issue #26; installed Release owner UAT pending
- Date: 2026-08-03
- Supersedes: only D-25-01's no-retry and immediate-recoverable-failure clauses
- Affected boundaries: Feishu session teardown, coordinator retry/replay, release races, partial
  delivery, current-focus output, terminal feedback, privacy diagnostics

## Context

Installed Release evidence showed one hold accepting two HTTP-200 streaming packets before
`action=0, sequence_id=2` returned HTTP 200 with business code `10024`. Three later fresh holds
received the same code on `action=1, sequence_id=0`. Each rejected response produced one
application error; this was not recursive publication of one callback. The failed established
stream emitted neither action 2 nor action 3 because the client recorded recognition failure before
`cancel()` checked abort eligibility.

Current official [Feishu endpoint documentation](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/ai/speech_to_text-v1/speech/stream_recognize)
and the [generated Lark SDK](https://github.com/larksuite/oapi-sdk-go/blob/8dfbfff01d210b20ec9473bf383d38d1b54aa37b/service/speech_to_text/v1/model.go#L544-L559)
do not define business code `10024`. They document 100–200 ms audio chunks, action/sequence
meanings, a 20-concurrent-stream tenant cap, and other published error codes, but do not map
`10024` to pacing, quota, tenant edition, sequence, or leaked-stream state. The repair therefore
cannot depend on an invented provider explanation.

The same UAT also clarified the product interaction: recognized text should appear while Fn remains
held. Verified AX range replacement already provides that behavior for capable controls. The prior
unbound fallback waited until release, so AX-unavailable controls did not meet the requested timing.

## Decision

One accepted Fn hold is a generation-owned resilient interaction. It retains one audio capture and
one ingress until release, the 60-second cap, or terminal lifecycle invalidation. A recoverable
transport/session failure ends only the current Feishu attempt. The coordinator performs bounded
teardown, waits with capped backoff, creates a fresh serial streaming session, and replays the same
hold's ordered audio journal. No recoverable failure is shown to the user while Fn remains held.

When verified AX range replacement is unavailable, the first non-empty hypothesis gets one more AX
binding attempt. If live AX capability is still unavailable, a guarded current-focus session binds
the then-frontmost PID and provides best-effort continuous output by posting only the first value
and exact UTF-16 suffixes. It never deletes or rewrites previously emitted text.

### Typed retry policy

The outer hold loop retries only:

- `StreamFailure.network` and `.timeout`;
- HTTP 408, 425, 429, and 5xx;
- backend business code `10024`;
- API/session-factory `.timeout`, `.networkUnavailable`, `.connectionFailed`, and `.networkError`.

Malformed or identity-mismatched responses, invalid request/response, authentication,
recognition-contract failures, unknown/unclassified errors, other backend codes, and other HTTP
statuses are terminal to the hold. Audio ingress/capture and permission/security failures remain
lifecycle-owned because reconnecting cannot restore lost audio or trustworthy authority. Output
destination/security changes suspend automatic output for the hold; they do not authorize
reconnecting or retargeting.
Treating `10024` as recoverable is a FeishuSpeech product resilience policy, not an official meaning.

The hold-wide retry ordinal starts at one and never resets after a replacement stream accepts a
prefix. Base delay is 250 ms and doubles through 500 ms, 1 s, 2 s, and 4 s. Injected jitter is
clamped to 0.8–1.2 and final delay to 200 ms–4 s. There is no separate attempt-count cap; the
existing 60-second hold maximum is the absolute bound. Only one session and one request may be
active at a time.

### Exact-once failed-stream abort

Recognition outcome and remote teardown eligibility are independent:

- failure of action 1 before any packet was accepted emits no action 3;
- failure of an established action 0 attempts action 3 exactly once;
- failure of action 2 attempts action 3 exactly once at the next unconsumed sequence;
- successful action 2 permanently suppresses action 3;
- repeated `cancel()` calls cannot emit another abort;
- an in-flight action 0/action 2 is cancelled and action 3 waits behind the same request gate within
  the existing one-second total abort deadline; it never overlaps another request.

Abort acknowledgement affects diagnostics only. It does not reinterpret the failed recognition as
success and does not itself admit another attempt.

### One capture and ordered fresh-session replay

The sole ingress consumer appends every packet to a per-hold journal before its first send. A
failed packet therefore remains replayable. Each fresh session sends the retained packet elements
from index zero in order, without re-chunking, combining, dropping, parallelizing, or switching to
`file_recognize`.

The ingress enforces the 1,920,000-byte capture ceiling across delivered replay-retained packets,
queued packets, and pending coalescing bytes under one lock. Padding added to a short terminal tail
is not counted as additional captured audio. A byte beyond the hold-wide ceiling fails explicitly.

During catch-up, historical replay responses do not repeatedly mutate the target. The coordinator
retains only the latest accepted replay hypothesis and offers it once at the journal frontier, then
resumes normal live output. Audio captured during abort, backoff, and replay continues through the
same recorder and ingress.

### Release and lifecycle authority

Fn release and the 60-second cap set sealing before awaiting recorder shutdown. Sealing closes
admission to a replacement session and actively cancels retry-delay/session-creation waits. A live
attempt may drain the sealed ingress and finish once. A replaying replacement is cancelled once;
all cancellation callers await the same bounded cancel/action-3 work, and the resulting typed
cancellation is treated as release control flow. Local completion waits for the old recorder stop
barrier before idle can admit another hold. A recoverable failure after sealing preserves/routes the
latest usable result rather than opening another stream; no usable result produces one fixed error.

Reset, sleep/wake, security or permission loss, capture failure, and cleanup immediately invalidate
the generation and cursor/output ownership and cancel retry/current-attempt work. If recorder stop
is already running, its barrier is retained independently: it blocks successor admission and final
idle/error publication, but it cannot delay authority revocation or transport cancellation. Late
delay completions, factories, packets, partials, finals, and aborts are no-ops.

### Continuous output boundaries

Verified AX output remains authoritative: each opaque hypothesis replaces one app-owned range on
the captured element with pre/post range, caret, focus, PID, security, and generation checks.

If startup AX capture is unavailable and the first non-empty partial still cannot establish live AX
capability, `CurrentFocusAppendSession`:

1. binds the then-frontmost PID and monitors application activation;
2. rejects contentless or C0/C1/DEL-bearing text;
3. posts the first safe value as direct Unicode input;
4. posts a later value only when its UTF-16 units strictly start with all already emitted units,
   and then posts only the unseen suffix;
5. treats duplicates as no-ops and suppresses revisions, shortenings, and canonically different
   encodings;
6. samples Secure Input and the bound PID twice before and once after each post;
7. permanently suspends after activation away, PID mismatch, security rejection, delivery
   uncertainty, or generation invalidation;
8. never uses Backspace, selection, cursor navigation, pasteboard mutation, rollback, or an
   uncertain resend.

An exact or extending final may commit or add one suffix. A divergent, shorter, unsafe, or empty
final preserves already visible text and does not fall through to one-shot current-focus insertion
or clipboard recovery. `autoInsert=false` creates no AX/current-focus writer and performs no target
or pasteboard mutation.

This path cannot observe a caret move between controls inside the same process. Stable PID therefore
does not prove stable caret ownership; a later suffix may reach a different caret in that process.
This residual risk is accepted for the scoped best-effort behavior and must be exercised in owner
UAT. Universal revisable output in AX-unsupported controls would require a separately approved
composition-capable input method/IME.

### Feedback and privacy

A recoverable in-hold failure produces only a sanitized typed/numeric diagnostic. It does not set
an error state, call the hot-key error path, hide/re-show the overlay, write/copy text, or post a
system notification. At most one terminal user-facing outcome is produced after the generation is
claimed. Logs and diagnostics continue to exclude transcript text, audio, credentials, tokens,
stream IDs, raw response bodies/messages, target contents/titles, and clipboard payloads.

## Consequences

- A transient provider/network failure no longer ends an Fn hold immediately or repeatedly exposes
  the same generic error across owner retries.
- Failed established streams receive one bounded best-effort remote abort before a successor is
  admitted, reducing client-created abandoned-stream risk without claiming provider semantics.
- Replay preserves audio order and continuity but may resend audio the provider accepted before an
  ambiguous failure; fresh stream identity and serialized ownership contain that ambiguity.
- AX-capable controls retain safe revisable replacement. AX-unavailable controls gain immediate
  monotonic output, but revisions are intentionally suppressed and same-PID caret movement remains
  unobservable.
- No production behavior falls back to whole-file recognition or destructive synthetic editing.
- Focused automated suites are green, but the new behavior does not claim installed Release,
  credential-bearing, action-3, retry/replay, or cross-application UAT success.

## D-25-01 supersession boundary

This decision supersedes only these D-25-01 claims:

1. an established stream is never replayed through a fresh streaming session; and
2. every stream failure immediately terminates the whole Fn generation and publishes failure.

D-25-01 remains authoritative for opaque partial semantics, verified AX range ownership,
generation safety, security fail-closed behavior, privacy, final preservation, no destructive
editing, captured final-only delivery, and the ban on whole-file fallback.
