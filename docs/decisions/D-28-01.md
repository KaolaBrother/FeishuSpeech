# D-28-01: Capture/recognition split and preferNoProxies fallback

- Status: accepted
- Date: 2026-08-20
- Issues: #28 #29 #30 #31

## Context

Holding Fn started the microphone immediately, but the only PCM consumer waited on Feishu factory
before journaling packets. A hung or proxied `URLSession.shared` path then mapped transport cancel
as hold-terminal, so the overlay stayed on `正在聆听…` with nothing to replay after teardown.

## Decision

One Fn hold has two concurrent `@MainActor` unstructured tasks: a capture line that is the sole
ingress iterator into `HoldPacketJournal`, and a recognition line that waits on that journal.

In-attempt `CancellationError` / `URLError.cancelled` / transport-origin `StreamFailure.cancelled`
is recoverable timeout while retry is open. Generation cancel stays terminal.

Streaming factory, token refresh, and `stream_recognize` use a per-attempt `URLSession` with
transport-owned slice timers. When that slice produces no HTTP response, the same watched operation
falls back once to an attempt-scoped HTTP/1.1 keep-alive `NWConnection` to `open.feishu.cn:443`
with TLS SNI `open.feishu.cn`, required peer authentication, no custom verify block, and
`preferNoProxies = true`. Completed HTTP (including 401/407/403/unparseable 400) does not hop.

## Consequences

- Peak PCM is about 2× because ingress retain-true stays on.
- Tenant-token POST may run while `NWPathMonitor` is unsatisfied; it is not sent if TLS fails.
- Direct is sticky for the rest of that attempt only. The next factory starts on URLSession.
- Keep-alive leftover is the raw framed end of one HTTP message, including chunked trailers.
- One-shot `DirectFeishuHTTPClient.send()` and any CDN IP list stay out of the production path.
- Overlay copy is unchanged. The menu extra is icon-only so it is not lost in the MacBook notch.
