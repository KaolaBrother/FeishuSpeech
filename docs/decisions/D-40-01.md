# D-40-01: Review fallback bound to the original application after a non-secure AX miss

- Status: accepted and implemented; focused automated validation complete; installed Release UAT pending
- Date: 2026-08-23
- Issue: #40
- Supersedes in part: D-38-01's strict-AX-only review startup and delivery admission
- Retains: D-38-01's review-first lifecycle, exact-cursor route, clipboard transaction, manual recovery,
  and independent capture/recognition axes; D-39-01's Return/Enter keyboard policy

## Context

D-38-01 correctly required review-first to bind the original destination before audio or provider
work. Its strict capture contract, however, treated an ordinary non-secure editable target that
could not expose a complete AX cursor, selection, or settable attribute as a startup failure. That
made the review surface show `无法确认输入位置` even when the original application was identifiable
and safe to reactivate.

Issue #40 adds a weaker, explicitly typed review authority for that one case. A complete original
application identity is captured before the panel, recorder, or provider starts. A safe exact AX
cursor remains preferred. When only the strict cursor contract misses for an ordinary non-secure
target, confirmation may reactivate that exact application and use its current focus. This is an
application-bound fallback, not an ambient-focus or cross-application fallback.

## Decision

### Typed capture outcomes and identity-first ordering

Review destination capture has two successful bindings:

- `ReviewDestinationBinding.exactCursor(CursorDestinationToken)` — the D-38 route, including the
  original `AXUIElement` and selected range;
- `ReviewDestinationBinding.applicationCurrentFocus` — the original complete application identity,
  with no AX element, selection, second PID, app name, or transcript.

`ReviewDestinationToken` carries the positive interaction generation, the complete
`ReviewApplicationIdentity` (PID, bundle identifier, executable URL, and finite launch date), the
binding, and a captured `.safe` security state. Exact cursor generation/PID must match the
application identity. The fallback intentionally carries no cursor that a caller could mistake for
exact authority.

`MacAccessibilityClient.captureReviewCursorDestination` returns a typed
`ReviewCursorCaptureResult`:

- `.exact(...)` for a supported safe element with a valid selection and settable focus/range;
- `.nonSecureCursorUnavailable` for a capability miss after trust and live Secure Input checks
  remain clear; and
- `.rejected(.secureInput)` or `.rejected(.accessibilityUnavailable)` for a secure or untrusted
  condition.

`SystemReviewDestinationDelivery.capture` first captures the frontmost complete application
identity, confirms that the running process with that PID has the same identity, then asks AX for
its typed result. It revalidates both running and frontmost identity afterward. Only an exact result
or an ordinary non-secure capability miss can be admitted. Missing identity fields, PID reuse,
identity drift, lost Accessibility trust, global Secure Input, or an affirmatively secure AX role
map to a terminal startup rejection. The fallback never binds an application discovered after the
review panel changes focus.

### Lifecycle and asynchronous boundaries

Both bindings are captured before `showOverlay`, recorder/ingress setup, `captureDrainTask`, the
recognition consumer, provider startup, or the first review render. Once accepted, both use the
existing one-panel streaming -> sealing -> editable flow, action-2 and recorder-barrier ordering,
synchronous confirmation consumption, and exact untrimmed draft freezing. D-39-01 is unchanged:
unmodified Return/Enter confirms, Shift+Return/Enter inserts LF, Command+Return remains available,
and marked-text Return stays with the input method.

The capture/journal producer and recognition/factory/retry/replay/consumer line remain independent.
Review rendering and delivery introduce no wait, continuation, buffer, or backpressure edge to
either line. Review-first still never writes recognition text while Fn is held or while action 2 is
settling.

### Confirmation delivery

The exact binding retains D-38 ordering: activate the captured application once, focus only the
captured AX element, restore and reread its original selection, recheck identity/frontmost/security,
then perform one process-targeted Cmd+V transaction. Exact AX restoration remains preferred whenever
it is available.

For `applicationCurrentFocus`, no AX setter or later AX recapture is allowed. After activation, two
consecutive pre-mutation samples must keep Secure Input off, the raw frontmost PID equal to the PID
in the captured identity, and both the running and frontmost complete identities equal to that
identity. `SystemFinalTextOutput.insertReviewAtCurrentFocusOnce` writes the exact untrimmed multiline
draft and posts one Cmd+V pair to that captured PID. It never discovers or substitutes an ambient
PID. Each preflight composite is ordered Secure Input at start -> raw captured PID -> running and
frontmost complete identities -> Secure Input at end; postflight uses the equivalent composite
safety shape.

Activation, security, PID, identity, unsafe-text, key-post, or postflight uncertainty is terminal.
There is no automatic retry, retarget, AX recapture, or clipboard restoration after a possible post.
The existing coordinator recovery path copies the frozen draft exactly once for a current
non-cancellation failure; cancellation copies nothing. Text safety continues to admit LF and
reject NUL, tab, CR, DEL, and C1 controls before mutation. Successful exact and fallback delivery
share the full pasteboard snapshot and `changeCount`-guarded restoration transaction.

### Capability limit

The fallback proves the exact original application, not the original control or caret inside that
application. After the review panel is dismissed and the application is reactivated, delivery uses
that application's current focus. It cannot restore an unavailable AX element or selection, and it
cannot cross to whichever application happens to be frontmost. Supporting unavailable intra-app
control/caret authority would require a different platform mechanism and is outside Issue #40.

## Consequences and UAT boundary

An ordinary final-only or editable target that previously missed the strict AX cursor contract can
now open the review surface and complete the same preview, sealing, editing, and confirmation flow.
The startup message `无法确认输入位置` remains expected for global or affirmatively secure input,
lost Accessibility trust, incomplete application identity, PID reuse, or identity drift. A target
that reaches fallback confirmation still needs owner UAT because `CGEvent.postToPid` has no
application-level acknowledgement that a third-party control consumed Cmd+V.

The installed Release UAT matrix must include at least: one target that previously showed
`无法确认输入位置` because of an ordinary strict-AX miss, one exact-AX target, Secure Input and
secure/password rejection, an application switch during confirmation, a multiline draft, and a
forced post/postflight uncertainty with one-copy manual recovery. UAT must verify visible behavior
without claiming that local event submission proves target acceptance.
